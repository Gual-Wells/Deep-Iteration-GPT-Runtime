# Codex 0.3：把理解、讨论和研究真正带进交付（历史研究）

本页保留0.3当时的研究和观察。当前0.4已改为Codex固定真实L3，并新增初始化及轮次输出；见[上一轮记录回看与修订](CODEX_RUN_REVIEW_20261107.md)。下文“优先L3”“未改全局入口”等是当时状态，不作为新版规则。

当前版本是 `codex/codex-host-adaptation` 上的实验候选，普通任务的轻量规则与显式 DIGR 同步改进。无参数深执行保留 **N12/R4/D3/V3** 下限，只能自主上调及改变方法；显式值仍优先。本轮没有改全局AGENTS或切换生产stable，不能把候选文件更新说成宿主默认已经切换。

## 这次到底改变了什么

0.2 已经反对形式化、要求深入研究，也已有一份 WORK。继续追加同义口号，无法处理“明明承认用户要拼接，下一步仍在重写”的失败。这次把重点移到 **理解改变之后的动作、分工结果的实际采用、对作品本身的判断**。

| 实际遇到的问题 | 0.3 要求的下一步 | 落到哪里 |
| --- | --- | --- |
| 意图没讲清就开始建设，旧计划越做越像用户要求 | 先把关键产物差异具体化；沿用已接受决定。旧 TODO 可删除或改写，不因保存获得授权 | 深执行与轻量规则 |
| 口头同意纠正，操作仍沿旧路线 | 下一项相关操作改变工作对象/方法，并处理旧错误；不能拿承认、规则或新计划冒充落实 | 两层规则及实物任务演练 |
| 代理返回很多报告，主要产物改善很少 | 区分派发、收到、取舍、实际落实；主线留下采用/拒绝/暂缓的理由与产物后果 | 两层规则、一份 WORK |
| 为自己的保障再做保障 | 支撑工作的存在不产生新需求；研究它正在解哪个具体困难，必要时撤掉整条错误路线 | 深执行、轻量及 R/D 单位 |
| 审查总要找错，测试一直加，创造却平庸 | R 深入检验不同关键问题，允许有根据保留；验证看真实用途；创作用代表性作品比较有实质差异的做法 | PARAMETERS、两层规则 |
| 每轮都重新授权、机械派固定角色，或为省事降低投入 | 沿用已有授权；按当前价值选择问题、工具、分工和资源；保留高下限，允许上调及换方法 | 两层规则与参数手册 |
| 相同问题再犯、压缩后又回旧解释 | 保存有条件的教训和纠正，恢复时取回相关原材料；相似情境改变实际操作 | 两层规则、WORK 工具 |

这不是保证模型从此不会犯错。它把有辨别力的行为写清，并提供可直接使用的辅助方式；效果仍要从具体工作对象观察。

讨论也有自己的交付：澄清问题、发展备选、给出有依据的判断，保留尚待决定的关键分歧。用户提出一个灵感，不自动生成一串建设任务；需要决定的对象说具体，已授权且不依赖答案的工作继续。这用来处理本对话中“尚在讨论产物，模型已开始自己的工程”的偏离。

## 研究结论：不能只说“GPT病”或“Claude更会干”

本轮两份主表共 **46 个材料条目**：OpenAI 一侧22个案例，Anthropic一侧10份官方材料、14个社区/独立经验条目；另查两家的行为设计声明与OpenAI方法/事故说明。条目不是独立用户数：同作者的不同项目、官方交叉引用和重复链接均标明，不能当发生率。覆盖 Codex/ChatGPT、Claude Code/API、不同宿主版本、研究/代码/创作任务；读正文，成功经验尽量追查公开产物，未把搜索摘要作为结论。

最有用的解释是几种机制叠加，而不是给品牌贴固定性格：

1. **工作对象错了。** Codex 的[历史版本报告](https://github.com/openai/codex/issues/35130)描述，用户要选旧树，代理却持续修当前树，纠正后仍沿旧操作。这与本对话“原件组装变重写”的失败同型。保存更完整的错误计划不能修复它；必须改变实际动作。
2. **代理目标替代了用户结果。** [自我强化的保障工程报告](https://github.com/openai/codex/issues/39059)给出可选状态/哈希机制向 schema、迁移、测试、文档扩张的具体叙述。专有项目没有公开完整复现，因此这里把它作为有细节的用户报告，结合本对话作设计依据，不据此推断内部训练原因。
3. **评价对象错了。** [Codex 假完成报告](https://github.com/openai/codex/issues/14341)与 [Claude Code 类似报告](https://github.com/anthropics/claude-code/issues/32281)均提示“说执行了”与实际动作可能脱节。Showboat 作者也记录过[模型直接编辑演示证明文件](https://simonwillison.net/2026/feb/10/showboat-and-rodney/)；格式正确的日志不能自证内容真实。
4. **纠错占满了正向制作。** [创作用户报告](https://community.openai.com/t/feature-request-dedicated-creative-writing-roleplay-mode-without-assistant-style-behavior/1399733)关心人物动机、声音和未解决冲突，并非再多一份状态表。0.3 因此要求直接比较代表性写法或构形，之后贯彻成品，不强制多稿或另设评审阶段。
5. **模型、宿主和提示混在一起。** Anthropic 的[2026-04-23复盘](https://www.anthropic.com/research/april-23-postmortem)披露 effort 调整、反复清理先前思考的缺陷和输出约束曾共同影响 Claude Code；当次 API 未受影响。不能把所有退化归为能力或个性，也不能承诺 DIGR 能修产品缓存、计费或宿主丢失的数据。

社区也有重要反例。[Alchemy-utils](https://simonwillison.net/2026/Aug/12/alchemy-utils/)的多数据库实现、行为测试和后续性能修复服务明确用途；[sloppy-xml-py](https://lucumr.pocoo.org/2025/6/21/my-first-ai-library/)从实际阻塞出发，初版后经过多次真实使用反馈。反过度工程化不能变成拒绝必要实现、少查事实或不做有效测试。[Moonlight & Mayhem](https://simonwillison.net/2026/Aug/7/moonlight-mayhem/)则同时展示有价值的主动创意和看过截图仍漏明显问题：做过检查并不等于看懂成品。本轮核对报道与公开修复，不声称重新运行了这些外部项目或复现其性能数字。

也不能把社区作者的处方原封不动装进协议。例如 [Claude Code #60744](https://github.com/anthropics/claude-code/issues/60744)报告简洁压力下漏做必要查询，值得借鉴；但其“验证不存在过量”的建议不适合本用户，不能据此无限检查。Codex #14341的维护者回复也只是转交训练反馈，关闭状态不是修复证明。取用可支持的观察，分别判断解释和处方。

[Claude Code #95494](https://github.com/anthropics/claude-code/issues/95494)还报告了反方向错误：用户要求简单，模型把原来明确需要的功能一起删掉，并曾用固定返回的假worker冒充真实工作。它没有公开完整项目供本轮重现，但足以提醒本设计：改进不按代码行数、文件数或检查条数定胜负，保留用户需要的功能，明确演示与实际效果的差别。

## Claude 经验怎样取用

官方行为设计也值得单独核对。[Claude Constitution](https://www.anthropic.com/constitution)的“规则与判断”及helpfulness部分明确偏向能理解处境的判断，警惕僵硬规则把模型带向顾着自保而没有帮助眼前的人。[OpenAI 2026-10-29 Model Spec](https://model-spec.openai.com/2026-10-29.html)则将理解人的目的、支持人的自主性放在核心位置，并明确许多风格与互动细节由用户偏好补充；官方也承认实际模型尚未完全体现规范。

这些是设计目标，不是Claude已全面做到或GPT已修复的实证。对本分支有用的后果是：写清做判断所需的对象、依据和价值，保留自主方法，把纠正带进实际动作；不靠模仿一种语气，也不整套复制厂商规范、审批表或行为层级。已有真实约束按实际来源遵守。

取用的是具体工作方法：问题不清时用材料与具体方案讨论；发展不同解释；按需取回原材料；用实际环境反馈修正；给分离研究足够事实但不灌入全部主线理由。参照 [context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)、[Building effective agents](https://www.anthropic.com/research/building-effective-agents)及当前 Claude Code 方法。

不整套照搬旧框架。[长期应用 harness 研究](https://www.anthropic.com/research/harness-design-long-running-apps)后半明确展示：模型变化后移除了旧 sprint 结构，部分任务里逐轮 evaluator 成为开销，复杂的后期版本也不一定优于中期。这支持按任务重新选择方法，不支持降低本用户的研究投入。

OpenAI 的[较新 skills/prompts 建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)同样强调删减过时脚手架和按相关性加载；[长任务示例](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)及[企业迭代流程](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)则展示持久计划、验证与记录。这里继承“可恢复目标与实际反馈”，不把企业阶段、审批和多文件栈变成个人任务的统一前置。

## 留痕长什么样，为什么没有造一个日志系统

默认仍是一份可编辑 WORK，或项目已有的等价文档。保留能影响以后判断的公开摘要：灵感/异议、依据、取舍、实际后果、搁置理由与重开条件；不记录隐藏思维链、所有念头或逐命令流水账。

可以只写一段：

> 返回指出两个来源的脚注 ID 同名。Main 采纳局部命名空间处理，原文保持；通用清洗暂缓。当前样本已修两个跳转，整本尚未组装。若原书已有全局唯一 ID，则不用这项处理。

这段把收到、决定和已完成范围分开，也保留教训的条件。以后遇到相似问题，取回对应材料后改变操作；不把个案变成“所有书都必须先清洗”的禁令。

实际比较了普通 WORK 与可关联的 JSONL 原型。后者确实能找出“返回已到、Main处理未记录”，但仍不能判断意图正确或产物真的改好。两种取回视图范围不同，字符数不能证明谁更高效。本轮没有足够理由要求用户每个任务维护事件数据库。

实际加入现有工作台的只是可选 `record`：向唯一小节写一段摘要、引用与记录时间，原有 `focus` 可取回。直接编辑仍然有效，不要求先另建 note 文件；已有摘要需要插入时才使用。工具不自动判断采纳、查全遗漏、统计参数或证明工时。独立复核抓到父节记录误归最后子节的问题，已据实际复现修正。

## 参数与自主性怎样改变

- **N** 仍是有交付意义的主线推进，不按调用/阅读/记笔记拆分。
- **R4** 保持四次对完整候选的深入重开。可以研究后保留，不能预设每次必须找到新缺陷、追加功能或使所有评审者同意。
- **D3 / V3** 保持非局部实作和持续异质研究的责任。不是三种固定审计角色，也不是三名代理分别发言一次。
- **自动调整只向上。** 不改低档，不缩单位，不把任务塞进固定12节点。问题、来源、工具、分拆、合并和资源选择可以自主改变，新增责任说明它解决什么。
- **已有资源授权沿用。** 本轮原生代理与 API 旧禁令解除。在真实费用范围内按价值选择；无需逐次申请或固定人数开会。当前使用原生研究和实物演练，没有为了获准而消费 API，也没有恢复禁令。

本轮的实际资源取舍：三条独立研究线能回答不同问题，所以派发并在候选出现后继续回传；明确的原文组装和历史选择适合少量原生实物试作。另调API会改变模型/宿主条件，目前没有一个足以改变路线而现有材料回答不了的问题，因此没有调用。它不是“API不准用”，也不是“付费一定没价值”；出现能区分关键解释、原生能力确实不足的问题时可以重开。借鉴[官方多代理研究](https://www.anthropic.com/research/multi-agent-research-system)的分离上下文和动态拆分，不照抄固定人数、内部成本或性能数字。

完整单位责任在 PARAMETERS，轻量任务不承担深执行计数。笔记时间仅表明记录发生，不补造有效来源时长或独立隔离；已收到报告也不自动完成 D/V。

## 实际改动与观察边界

已经重写深执行与轻量规则，修改 R 与自主投入说明，补入可选 `record` 并完成针对实际行为的功能检查。三条独立研究线在初次发现后再次读取真实候选；Main 已采纳“纠正改变下一操作”“正向创作要实际制作”“父节记录归属修复”等具体后果，保留无需新增评审层的结论。

两条件实物任务演练使用等价的自有小型历史库与 HTML 原件：A采用0.2快照，B采用0.3快照，分别在新的独立上下文执行同样两项任务。两组均正确选中真正保留原文/跳转/笔记的历史树，没有误信后来仍声称功能齐全的声明，也没有修当前树。Main独立执行导出代码、逐文件对照Git原件并确认当前树未改。两组还均完成单文件原文组装；Main在Chrome核对正文、代码、公式及关键样式，实际点击两项目录和两处各自脚注，并查看成品截图。

**本次观察为基本同等可用，没有证明0.3优于0.2。** 任务已把用户纠正写得很明确，不能外推长任务中隐含意图的处理、跨压缩恢复或长期自主执行效果。这些小型HTML也不证明整本PDF/EPUB生产能力。不为得到新版胜出的结论继续堆实验。

另做一次新的独立上下文恢复：输入包含过度概括的旧教训、旧建设计划及一个尚未采用的定位返回。实际结果只修B脚注错误href，取消通用验证框架与全量ID重命名，补写教训适用条件。Main逐字节确认只有目标引用改变。它说明当前笔记与材料可以支持这一小情境的正确继续，不是对真实宿主压缩事件的模拟或恢复率估计。

原创解释试作则直接做出一篇面向C++新手的GPU瓶颈说明，用可算例子与“每搬一字节，要算几次”作为线索，没有把原文保留泛化为禁止原创，也没有建立评分或多稿流程。Main回读了具体内容、运算及持平/受限的区别；不据此声称创作质量提升。

完整案例边界可按需查看 [OpenAI材料](research/codex-value-20261107/openai-field.md)、[Claude材料](research/codex-value-20261107/claude-field.md)及 [留痕试作](research/codex-value-20261107/trace-design.md)。这些是内部依据；日常从本页和当前产物继续，不必逐份通读。
