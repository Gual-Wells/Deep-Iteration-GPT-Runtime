# Codex0.3 留痕、研究回传与自主投入：第一轮反对设计

2026-11-07。本报告研究候选 Codex0.3；本轮 P_run 仍是已绑定的 stable Alpha5，不因自举研发而改绑。这里只读取本地对象进行设计比较，没有用本地对象冒充本轮 live ref 权威。未改动 canonical `runtime/`、`codex/`、stable 执行核心，也未调用外部模型 API、发布外部内容或写入全局 Memory。

## 先给 Main 的实质判断

**默认维持一份有内容的 WORK.md；不要把完整事件系统设成 Codex0.3 的必经路径。** 用户要求的是值得保留的灵感、异议、判断和执行后果，不是每个动作都有回执。两种存储都可以保存这些内容，区别在于谁承担关系维护和取回成本。

应补的窄缺口是：能迅速看见“研究结果已经收到，但 Main 是否处理过仍无记录”，以及先前搁置的路线为何搁置、什么变化使它值得重开。收到结果、决定采用、实际进入成品是三件不同的事；它们无需三张表，但不能因“代理结束”被折叠成一次完成。

如果 Main 的初始方向是“单事件流作为唯一事实源、所有中途过程自动进入、派生工作台和避坑记忆”，本报告反对它成为默认。它会把记录变成新的任务，引入分类与关系协议，并把旧错误永久留在每次恢复的入口。**可选的关系索引有价值，完整的过程数据库尚无当前证据支持。**

这不是把 N12/R4/D3/V3 降低。高投入下限与每单位责任保持，显式参数保留；调整的是实际研究问题、方法、工具、资源分配、拆分和合并方向。没有固定任务树，也不以文件少或日志短代替实质研究。

## 三种实现确实有什么不同

| 实现 | 实际写什么/何时写 | 怎么继续 | 维护代价与失效方式 |
| --- | --- | --- | --- |
| A：一份可编辑 WORK.md | 有改变后续行动的发现时更新对应问题；在同一处用几句写派发、返回与Main处理；有必要才保留沿革 | 直接读当前问题，或用现有`focus --topic`；原材料按路径/页段取回 | 无新服务、无格式升级。关系靠人维护；压缩时可能删掉异议或未处理结果；写得好与否仍重要 |
| B：一个JSONL事件流，按需生成可读视图 | 同样的有价值判断，以一条公开摘要记录；派发/返回/处理用ID相连；只有Main一个写入者 | 工具选出未处理返回、投入约定、纠正与重开条件；需要时看具体问题沿革 | 可机械找“缺少处理关系”；会增加字段/索引/选择成本，旧错误容易反复进入恢复；不自动更准确、更短、更有价值 |
| C：复用工作台，增补极窄可选能力 | WORK仍是主要可编辑入口；原生派发工具已有的任务ID/消息不另抄全文，Main仅补“采用了什么/为何不采用/实际后果” | 既有`topics/focus/challenge`照常用；仅在回传容易遗忘时附带关系索引 | 最接近现有使用方式；若又强制双写WORK和JSONL，立刻退化成两套事实源，应避免 |

推荐 A 为默认，C 为下一步候选；B 留作当前确实发生回传丢失、跨上下文漏处理时的可选工具。选择依据是实际需要，不能规定“任务超过几个步骤必须开日志”。若使用 B，派生视图按需生成，不要求另维护可编辑 VIEW；WORK里只引用或概括当前理解，不复制同一套状态表。

对 A 的真正反对意见也应保留：一份精炼笔记可以写得非常好，却没有机械办法保证 Main 没有把未采纳结果删掉。B 对这一个问题确有能力差异；因此也不应为了文件少，永久封死事件关系索引。

## 该留下什么，不该留下什么

记录公开、可检视的判断摘要、依据和行动后果；不存隐藏思维链、穷尽式内心独白或每个未成熟念头。可在实际工作结束一个有价值片段时顺手留下，不要求每次调用工具前后填表。

值得保留的例子：

- 用户纠正改变了当前任务表征，或明确放弃/保留某种交付形态。能取得原话时保留原话和位置；自己的解释与原话分开。
- 一个灵感或异议能威胁当前路线。即便尚不能执行，也记下待区分的问题及可观察条件，不只写“还有另一种可能”。
- 派出去的问题、给了哪些关键材料、真实返回了什么。主线至少在需要继续或准备交付时看清哪些结果未处理，不要求收到每条消息就立即停主线开会。
- 采用、部分采用、拒绝或暂缓的有内容理由及实际后果。若只改了计划，应直说尚未进入成品。
- 失败暴露了可复用原因；写“什么条件下会错、为什么、下次最省事的纠正、何时不适用”，而不是“以后所有任务都先做X”。
- 新材料改变方法/资源/研究方向，或使原来搁置的路线重新值得研究。保留原搁置理由及新变化，避免把重开写成无理由反悔。

一般不另记成功命令、打开文件、例行格式修正、重复测试通过、每条进度消息或没有后果的角色发言。真实失败若已经在工具日志里可直达，只需引用和解释其任务后果，不再抄一份长日志。

“将来恢复这项问题时，这条内容是否会改变判断或行动？”是编辑判断，不是给每条记录打分，也不是记录准入审批。有价值却尚无明确行动后果的想法，可以以待研究问题保留；不强迫把每个想法都包装成已验证结论。

## 任务分发与反馈：少一层安排，多一个真实取舍

原生工具已经给出的 agent ID、派发消息和返回物尽量直接引用。输入应让研究者能理解用户用途、已经确认的要求、当前独立问题和必要材料；不能要求它照着 Main 的完整解释续写。研究者可以带回“这个问题划分本身错了”，而非只能交付指定表格。

Main不用等待所有分支整齐收尾才工作；可以根据一个关键返回提前改变主线、再收窄/取消失去价值的剩余研究，也可以重开被拒的路线。只在记录里留下有意义的分工变化与原因。

反馈最小形态可以是一段：`返回发现A；Main采纳B、暂缓C，原因D；现在修改E；C在条件F发生时重开。` 不把这句话作为新认证。真实产物 E 没有变化时，不能仅凭“现在修改”声明已经落实。

对于持续 V，保留它在追究的不同问题和当前发现即可；当主线候选发生实质变化，再给必要新材料继续研究。没有新候选或新问题时，不为证明“持续”强迫它定时说话。存在跨问题合并、分拆或换视角时据实调整，不能固定成“安全、审计、规范”三人组。

## 自主参数：承诺、工作目标、方法与实际完成不要混成一个变量

本次不得下调 N12/R4/D3/V3，显式参数保持原义。程序可以帮助展示原输入、已补齐的投入约定及当前更高的工作目标；不能替模型判定一个推进的责任是否完成，也不能把事件条数自动换算成次数。

若原约定为N12/R4/D3/V3，研究中新出现高价值依赖，可把工作目标上调为N16/R5/D4/V3，同时增加独立研究、换材料、重拆问题或集中主线。不是先生成固定16节点树再把工作塞进去。若原显式N为16，至少保留16；若显式L3，不因当前方法麻烦就标签降为L1。真实能力/资源冲突按原协议处理，而不是靠改名消失。

上调的原因应是当前问题需要什么，不是“为了体现高投入”。已承诺的更高责任也不能在临近结束时无声回退。在本轮 stable P_run 中，研发目标的工作目标不重写被冻结的契约。

S/n/r同样保留问题尺度：一个来源工作面负责哪个问题，证据怎样改变判断，何次重新研究推翻/保留了什么。留痕可以引用这些公开结论；没有原始材料和实质研究，不能由URL或事件条数反推其完成。

`recorded_at`只证明记账发生的时间。它不证明记录之前一直在MAIN/SOURCE，不补回过去缺失的S/n/r计时，也不能把并发代理时间相加给T/t。若需要有效时长，继续使用本轮协议允许的真实活动区间/时钟证据；新日志仅引用现成证据，不以“每条事件打时间戳”替代计时。

## 避坑记忆的边界

留在本任务已有笔记中的条件化线索足够开始。比如：`跨章保留原HTML时，章内唯一ID会冲突；若真实跳转对出错，用源章节命名空间局部修复；源ID已全局唯一时不适用。`

不要自动把每次失败提炼成全局AGENTS/Memory规则。否则本次局部经验会使下一项任务先做不必要清洗，再次偏离用户目标。跨任务/个人记忆的写入仍按真实授权；本次未写全局Memory。候选工具可以检索任务笔记并展示来源与适用条件，是否迁移仍由当前问题判断。纠正了旧解释时，保留简短的“原解释已被何证据替代”，不要让旧错误与新事实以同等权威出现在入口。

## 真实可运行试作与结果

试作位于 [prototypes/trace](prototypes/trace/)。两个实现使用同一小情境：用户纠正、搁置整库重排、派发独立依赖研究、异议、返回缺6.3/脚注、Main部分采用、另一项anchor研究返回但故意未处理、局部重开、投入上调、条件化避坑线索。情境根据交接问题重建；它不是本轮真实书籍生产记录，也不把重建段落冒充用户逐字原话。

本次实际执行了两种取回方式与以下行为检查：

| 本次实际观察 | 结果及其含义 |
| --- | --- |
| 一份纯Markdown由现有`focus`取回派发小节 | 780字符，含用户纠正、投入约定、部分采用和未处理的anchor返回。说明现有工具已能服务这个小案例 |
| JSONL按`relates`形成派发→返回→处理视图 | 准确找出T0009/T0010为“已回传，Main处理未记录”；已经部分采用的依赖研究未被误列为待处理 |
| 初版事件视图 | 1,954字符，重复展示重开记录；该发现已用于删除重复显示 |
| 修正后仓库内示例视图 | 1,753字符，仍长于上述WORK焦点。它有自动关系找漏的收益，没有证明更省注意力 |
| 后续重开 | 能同时取回最初搁置理由与新出现的跨页图注问题，未把重开错误扩展为恢复全库清洗 |
| 投入上调与下调尝试 | 样例从N12/R4/D3/V3提高为N16/R5/D4/V3；原floor与显式L3保持。一次降至N3/R1/D1/V1的尝试被拒绝，文件未增加记录 |
| 工作台`challenge`的真实运行 | 保留用户纠正，不自动带入已经收到的anchor研究结果；后者仍需按新问题显式选入。应保留受控输入，不直接灌入全历史 |

两种输入均保留了足够恢复信息；这不构成真实长任务中的优越性比较，也没有测量真实人工维护时间。两种视图取回范围不同，B还包含跨问题的重开与避坑线索，字符数仅描述各次输出，不构成等内容的效率比较，也不能据此宣称A更优。这些长度数字不能作为选择A默认的效率证据；A默认的理由是现成能力已满足这个案例、无需强制双写，而不是长度竞赛。JSONL与WORK是为比较而并列保留的两个替代方案，产品使用不要求双写。13条情境事件不是N13，也不是已完成D/V或真实L3。

### 直接运行

仅需现有Python标准库，无安装、网络或API。输出目录必须是新的D盘目录，脚本不覆盖旧工作：

```powershell
python -B docs/research/codex-value-20261107/prototypes/trace/demo.py --out D:/CodexData/tmp/digr-trace-your-new-run
python -B tools/codex_workbench.py focus --work D:/CodexData/tmp/digr-trace-your-new-run/WORK.md --topic "派发、异议与主线处理"
python -B docs/research/codex-value-20261107/prototypes/trace/trace.py view --journal D:/CodexData/tmp/digr-trace-your-new-run/events.jsonl --topic "局部重排"
```

仓库内已生成的A输入是 [example/WORK.md](prototypes/trace/example/WORK.md)，B输入是 [example/events.jsonl](prototypes/trace/example/events.jsonl)，B派生样例是 [example/VIEW.md](prototypes/trace/example/VIEW.md)。实际第二次试跑输出在`D:/CodexData/tmp/digr-trace-study-20261107-r2/`。VIEW只用于这次检视，不是另一份需要人工更新的工作文档。

`trace.py add --journal ... --event ...`接受一条公开摘要的JSON对象；`kind/topic/summary/effect`是最小输入，其余按需要提供。`kind`允许自由名称，不构成所有工作必经的固定状态机；只有`dispatch/return/decision`关系参与待处理视图。示例采用单写入者，未解决并发写入、崩溃截断恢复、长期索引或自动摘要；不得把它作为生产调度器。

## Main应采纳、拒绝与继续研究的内容

采纳：在既有问题笔记里保留公开判断、依据、后果；把派发/回传/处理区分开；保留条件化重开与失效条件；保持高投入/显式值，允许方法资源和问题拆分动态改变；按需取回原材料。可以把关系找漏做成既有工作台的可选命令，先解决真实漏处理，再考虑更广工具。

拒绝：默认全量事件源；额外TRACE/DECISIONS/DELEGATION/PITFALLS四套文档；定时发言证明持续性；由日志数计N/R/D/V/S；用时间戳修补缺失时长；自动把经验写成全局指令；先铺满高下限任务树；把一段“采用”文字当成主要产物已经改变。

应继续研究而非直接定案：在下一次真实多轮长任务中，纯WORK是否确实漏掉返回，关系索引是否因此改变了Main行动，恢复时是否减少重复开题，哪些旧异议被有理由地重开。检查发生这些后果的具体片段即可，不需再建大套评分系统。

最后一个强反对意见：**这些规则都不能代替意图讨论。** 若Main仍未和用户就原文拼接、处理粒度和“完整”具体意味着什么形成理解，记录系统只会更牢固地保存最初误解。代表性原材料、可讨论小样与真实异议必须能够改变方案；记录的价值在于让这种改变可继续，不是让流程看起来完整。

## 成本与API价值判断

本次未调用付费API；代码无外部依赖和常驻进程，新增文件均在D盘。核查时C约9.42GB、D约104.81GB空闲；这些是本次采样，未将数据转存C。示例每个方案仅数KB，不需为此迁移共享环境。

当前问题是Main是否理解并处理返回，不是缺少一个模型总结接口。为13条公开记录付费自动摘要没有已证明的增益，且会新增调用、失败恢复和版本漂移。若未来真实任务显示原生独立研究仍持续同质化，可另用少量真正不同条件的盲看/替代试作检验外部模型是否给出改变方案的独特发现；先约束范围与成本，再讨论调用。当前不建议为留痕单独接API。

## Main候选返回后的再研究

Main已据第一轮反对意见调整候选：默认继续一份WORK，不预设JSONL为唯一真相；只保留确有收益的“派发→收到→Main处理”取回，考虑在现有工作台增加极小的`record/timeline/retrieve`能力。本节是对这项新候选的回应，不再扩测试代码。

### 反例：日志完整，产物理解仍然错

考虑一份完整记录：原要求保留为“拼接原PDF/EPUB”，Main却把“学习读物完整”解释为“必须统一叙事与重写”；随后如实记录全文清洗、147次付费重构、重写线路的三项异议及各自处理、样式改善、代码检查和目录完善。派发、返回、决定、工具证据全部相连，Markdown也精炼可读，所有旧异议都有处理理由。然而最终完整原书仍不存在。

在A中，完整笔记只是忠实叙述错误路线。在B中，`feedback`会报告所有返回都有Main处理，`view`仍会显示一份关系完整的错误路线。两者都没有语义机制判断“原文拼接”是否被Main擅自替换；有`exact_text`字段也不会自动发生理解更新。格式本身不会否定错误，模型仍需真正回到原始用途、原材料和代表性候选重新研究。不能以“记录全了”推断意图已经对齐。

本试作里的成功也有这一前提：用户纠正已经发生，样例作者把它正确放进了两种输入。它验证取回纠正，没有验证模型会主动发现初始误解。应把功劳归于实际发生的理解与方案改变，而不是字段。

有内容的讨论可以非常具体：拿同一小段分别做“原页组装”和“重新叙事”小样，比较用户拿到后能做什么、保留了什么、改变了什么，问或判断哪一种符合已给要求。原要求已经明确时直接沿用，不增设每任务必经的问卷或审批。若依然有决定产物的重要歧义，才向用户展示具体差异讨论；同时继续不依赖答案的工作。

### 对极小工作台扩展的建议

1. **优先加`record`，复用已有小节。** 把一段公开判断追加到当前问题下面，必要时带依据和后果；从结构化工具参数或文本文件读内容，保留真实换行。无需初始化另一套目录、运行ID、哈希链、状态对象或固定任务树。找不到唯一目标小节时明确指出，别静默写到错误问题下。
2. **`retrieve`先明确相对`focus`多了什么。** 当前`topics/focus --topic/--material`已经能取回问题与原材料。只有实际需要按词/关联任务ID跨小节找到旧判断时，再补检索；不能为了命令齐全把focus改名重做。结果保留原位置，带必要前后文，模型仍负责判断相关性与取回范围。
3. **`timeline`可只读，但不能自动承担时间证明。** 沿用实际记账时间或文本先后，展示选定问题的公开判断变化；未知发生时间就保留未知，不能把文件mtime或追加时间补成有效工作时间。不要让默认输入变成所有问题的完整时间线。
4. **可靠的关系找漏需要一点显式关系。** 自由文本、完全零约定、自动准确判定“尚未处理”不能同时获得。可以在确需找漏时引用原生任务/返回消息ID，并由Main记一条针对该返回的处理；也可以只检索含“待处理”的段落交给模型阅读，不声称已经推导状态。不要让旧处理自动覆盖同任务后来新返回的结果。
5. **不要求双写。** 若一段判断已在现有问题笔记里，record可直接把它当作当前记录，不再抄一遍到timeline文件。原生工具已经留下派发/返回全文的，就引用现成事实；Main补的是自己的取舍与行动后果。

建议Main先实现一个直接帮助现有笔记的record入口，并让现有focus承担主要继续能力。只有真实出现跨小节找漏成本时再加retrieve/timeline；这不是削减研究投入，而是把工具建设限制在已发现的效用上。

### 对已实现0.3候选的实际复核：record值得保留到什么程度

Main随后实际加入`record_work`和CLI `record`，并更新了PROTOCOL、轻量层、PARAMETERS与WORKBENCH。本次读取当前差异后，在D盘复制现成`codex/examples/assembly/WORK.md`进行一次插入与取回，不新增另一套系统或测试框架。

**对直接编辑的增益很窄，但真实存在。** 代码提供唯一小节定位、正文引用以免Markdown标题变成新topic、BOM/换行保留及插入位置返回。这是一个可选的写入便利，不是新的理解、调度或交付能力。已在编辑器或apply_patch中处理该笔记时，直接编辑往往更直接；CLI若每条记录都要先创建note.txt，会新增一个输入文件与一次操作。因此建议只在已经有公开摘要、或确实需要这类准确插入时使用，不让“顺手记录”变成“先造摘要文件才能工作”。既有任务消息/结果文件仍以引用为主，不整份抄入WORK。

**发现一处真实的section归属问题，已交回Main。** 当默认目标“研究、竞争解释与方案”含有多个`###`子节时，发现时的实现把通用记录插到整个父节末尾。Markdown并无“返回父节正文”的隐含边界，因此该记录也归入最后一个子节。实物中原本不含留痕工具判断的`focus --topic "已搁置的全量重排路线"`，插入后带回了那条与重排无关的通用判断。标题清单完全未变，所以只检查topics数量不会发现这种取回污染。

本次副本为`D:/CodexData/tmp/digr-record-review-20261107/WORK.md`，record返回第33行。正文示例是“默认继续一份WORK；只在真实出现返回丢失时考虑关系索引”，不是虚构的原书发现。该演练没有改变canonical文件。建议目标含子节时插到第一个子节之前，即父节自身正文末尾；叶子节仍插到本节末尾。这样修正已有section语义即可，不需新schema、禁止父节写入或另建日志。

**没有发现日志自证完成的新语义。** 当前`record_work`只写入并返回位置；不调用计数、隔离或采纳验证。PROTOCOL已经把派发、收到返回、主线取舍、进入成品区分开；WORKBENCH进一步明说工具不推断未处理关系、不认证采纳落实、不统计N/R/D/V。PARAMETERS保留充分研究后拒绝D结果也可以完成责任。这些边界已足够清楚，不建议为此再加回执或审查层。

整套0.3候选现在更贴近本轮目标：支持实质讨论、方法变化、条件化经验与主线综合，同时保留高投入。此次复核没有从中推出“工具已证明长期效果”或“规则已能阻止再次误解”；实际意图更新、产物行为和多轮使用后果仍由当前工作承担。除了上述具体归属问题，未为维持反对姿态另造缺陷。
