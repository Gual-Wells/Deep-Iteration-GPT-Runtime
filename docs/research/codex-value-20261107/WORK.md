# Codex 0.3：让留痕、研究和自主性服务实际任务

## 用户目标

结合DIGR整库、实际对话失败、OpenAI/Anthropic官方材料与大量社区案例，改进Codex默认轻量行为与显式深执行：更准确地共同理解意图和设计产物，减少自造保障工程、过量测试、无结果忙碌、平庸模板与假执行，保留有用的灵感/异议/决策及任务分派/结果处理，避免反复犯相同错误，增强自主推进。

## 交付形态与价值

可使用的Codex候选协议、必要的小工具改进、有来源边界的研究结论及少量真实任务演练。用户只需一个当前说明入口；分工材料是内部研究依据，不要求用户逐份阅读。不能用记录、验证或高数值代替实际结果。

已比较一份可编辑WORK、可选关系索引与强制事件流。采用WORK默认和可选小节插入；关系索引保留为有明确遗漏需求时可重开的路线，未升级为默认系统。

## 用户纠正与已确认要求

- 2026-11-07本轮补充：原生Codex/子代理及API旧禁令解除，可在任务内经实质价值与策略讨论自主选择资源；不等于必须使用付费调用。原有真实费用与权限边界继续适用，不另行购买服务。
- N12/R4/D3/V3保持下限，只允许上调及改变方法。不能以自主参数为名降低投入、缩小单位重量或凑形式工作。
- 默认轻量＋显式DIGR深执行保留；原件与既有有效成果保持。本轮改进候选，不自动替换stable。

### 已核实的起点

0.2已有一份WORK、目标与纠正取回、受控D/V材料和单位责任。实际长任务仍出现事后归纳计数、多个分工笔记直接交用户、收到研究与主线实际处理未充分区别。继续增加通用规则或完整事件数据库本身不保证改善。

stable/main已有候选、来源、D reintegration和状态持久化的精细实现，值得借用“结果须回到主线”的责任，不能把整套多store/receipt直接搬成普通Codex任务的维护前置。

### 事件：官方建议需要适用条件

实际读OpenAI的[skills与prompts更新建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)：过细指令、重复读文件和旧的thorough/test激励可增加负担；同时官方[企业工作流示例](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)展示很多阶段文件、审批与回顾字段。这里取用按相关性加载、只记实质事件及有依据复盘，不把企业流程冻结成个人用户的统一要求。

### 事件：独立研究已派发

- openai_field：按产品/版本调查具体社区失败、成功及反例；不把issue closed等同问题修复。
- claude_field：调查官方方法/事故、可看产物的经验与失败；追查宿主、模型和任务条件。
- trace_design：对普通Markdown和结构化日志做相同情境试作，主动挑战Main是否正在新建形式系统。

各线从受控任务包开始、没有完整Main历史。三线已在0.3候选出现后继续复研；Main采纳了正向创作方法、查询同步与父子小节归属修复，有依据保留R和无需新增系统的意见。不是只收一次意见。

### 事件：记录方式尚不能定为事件流

trace_design的首批实际比较：13条重建情境记录中，结构化视图能发现收到结果未处理；普通WORK focus也能取回相同的关键事实。其事件视图约1753字符，WORK focus约780字符，但取回范围不同，不能作为等内容的效率比较。初步后果：默认继续一份WORK，结构化索引若保留，必须有明确的小范围收益，不强制将全部讨论填成分类。Main又实际运行两种原型，确认这一窄差别；两种结构均不能判断最初意图是否正确。

### 事件：资源讨论的初步结果

社区研究线认为当前新增付费API收益不如外部案例与原生试作；Claude方法线已读到多代理/长评审成本增加且中间稿可能更好的反例。Main当前继续用原生研究，不因API获准就调用。这是当前策略选择，不能重新写成API禁令；候选真实任务演练若出现独立比较需求，可重新讨论。

### 复研：教训、社区处方和正式状态都不是永真要求

新的独立恢复试作读到旧计划、过度概括的ID教训和未处理返回后，只修了实际误指的href，取消自建框架与全量重命名。Main逐字节确认这一后果。它证明该小情境能正确继续，不等于真实宿主压缩恢复得到保证。

再查社区原文：Claude #60744的必要查询观察可以采用，“验证永不过量”的处方不采用；#95494里“简单”被执行成删需求，是反方向的失败。Codex #14341维护者只说转交反馈，不是已修复。82 tests那条无法分清新写与既有套件，不用它证明测试创作过量。源作者观点、观察与本轮判断分开。

main的EST与Strategy/Candidate再次核对：工作认识可被新材料替代，持续视角和返回须由主线处理；借用这个责任，不把多store/seal搬成普通任务前置。不可变协议pin与可修订研究笔记承担不同作用。宿主是否采用候选、真实工具是否执行，都不能从一条笔记或离线分发检查推出。

### 讨论的后果与保留的设想

本轮用户解除资源禁令之后，三线给出当前原生路线更有信息价值的理由；Main采用并实际完成原生演练。API仍可用，在有关键未决且原生能力不足时重开，而非建立新禁令。结构化返回关系索引则保留为跨上下文确实漏处理时可重开；目前不建。灵感不因被写下就成为建设承诺。
