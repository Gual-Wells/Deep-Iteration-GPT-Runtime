# 同线再入：完整作品与原生归档的对照

实际重读 Main 的 choice.json 与 ZIP 内全部六文件，逐文件字节对照所选 Git 树；候选确为 3e68f52cec21d59778233a547d051125cd107820。文件名集合、无重复/目录条目、每个 blob、原文原样、p1/p2 展示、两条导航与 n1/p1、n2/p2 关联均吻合。

初轮尚未解决的“作品完整性”现在落实到了两份非语义核心文件：reader.css 保留 44rem 宽度、1.7 行高及段落 2rem scroll-margin；release.txt 明确描述舒适行距与保留原材料。它们没有授权改写 RX-17，却是选中历史作品的真实组成部分。ZIP 确实带走了这两份原字节，未把旧版文字与另一版本的呈现文件拼接，也未带入 HEAD 的旧 PLAN。这里确认的是可重建的完整历史作品，不是浏览器视觉体验。

另外实际试作了一条完整备选路线：先由 reference 三文件计算 Git blob ID，在五个提交的树对象中作交集，只对两个幸存提交解析 HTML 的段落和导航，再用 git archive --format=zip 直接导出最新幸存提交。它独立选中了同一 SHA；内存 ZIP 为 1664 字节，Main ZIP 为 1515 字节，压缩容器不同但六个文件名与每个内容字节完全一致，且原生归档没有目录条目。

这条路线可竞争逐提交反复读取三文件、再逐 blob 手工组 ZIP 的实现：同一 blob 自带内容身份，Git 原生归档减少自行重建树的代码与出错面，不写 checkout、不改 HEAD，也不增加依赖或磁盘产物。但它把 jumps/notes 的相同性强化为 blob 字节相等，对只改 JSON 排版的合法版本可能过严；原生归档在其他仓库还需防范归档属性变换。本材料内已直接按归档输出核对相等，无此实际问题。五个小提交下性能收益不重要，因此没有理由要求 Main 改掉已验证的实现。

新增实算在 candidate_reentry.json，含六文件完整文本与 SHA256、双路线选择记录、原生归档对照。它是一条完成过实算的实现备选，未改变原作身份的判准；不凭“出现另一路线”宣布 D 或其他计数完成。未改 output、原件、HEAD 或工作树；Python 使用 -B。HTML 只作解析，未作浏览器可视化。
