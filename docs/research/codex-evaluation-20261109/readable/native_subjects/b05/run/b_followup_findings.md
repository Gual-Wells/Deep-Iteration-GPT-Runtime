## V：有限关系摘要是否足够支持可合并账本

新试作 run/b_relation_monoid.py 保留：正向支出桶、转账数、按目标id聚合的退款额、
每expense id的引用三态。三态为absent、singleton(category或None)、multiple。
只要两侧都存在同id的expense，合并态就是multiple；它不会因分类相同或金额0退化。
此操作是交换且结合的：非空记录数只需在2处饱和；分类只在总数为1时有用。
多个expense以后再追加任何expense仍不唯一，故不需保存每条expense的分类。

新反例证明singleton(None)不能并入absent：空账本与一个金额0/空候选expense(x)
最终三键结果完全相同；再合并expense(x,100,food)+refund(x,30)，前者得到food70/U0，
后者得到food100/U-30。省略这类零值/不可归类源记录会丢失未来唯一性信息。

run/b_verify.py 使用独立的O(n^2)逐退款扫描oracle，比较Main、完整替代及摘要模型；
固定随机材料同时核对目录为空、重复id、未知/重复候选、孤儿退款、类型间id碰撞、
排列、三分片合并结合律/交换律、输入/摘要不变及金额守恒，全部通过。
该新研究对Main的影响：没有发现候选语义错误，但其每id分类列表保存了退款永远
不会再使用的额外信息；在本题的静态追加模型内，可安全压缩。若增加删除/撤销源记录，
multiple吸收态将不再足够；本结论不外推到那种接口。

## D：独立完整替代，而非给上述验证贴标签

提案文件 run/b_budget_bounded.py，可独立导入并只导出所需summarize行为。
路线是第一遍验证所有金额，同时累计expense和transfer，并建立每id一个分类/None/
multiple标记；第二遍只解析refund。它不使用可合并摘要中的退款聚合索引，因此不会
为大量唯一孤儿退款另存字典；也不把任何单条expense或其分类列表保留下来。

与Main完整路线的具体差异：
- Main第一遍存每条expense分类，第二遍再次分类expense；替代只分类一次。
- Main辅助空间随expense条数增长；替代随不同expense id数及目录大小增长。
- 都需完整items可二次遍历；本题明确list，满足条件。
- 多标记是本次函数调用的局部对象，不产生跨调用状态；返回值不包含它。

已实际运行比较：30000条同id同分类expense加一笔30退款，二者均返回
food30000/U-30。tracemalloc从输入建好以后开始，仅测调用新增峰值：Main为247200
字节，替代为760字节。这是特定重复密集材料的观测，不是通用速度/内存基准。
独立oracle和金额拒绝行为比较全部通过；未声称现有固定任务要求性能优化。

替换主张：在保持当前规范和二次遍历list契约时，建议以此完整实现替换Main预算路线，
理由是保留恰好足够的引用信息、少一次候选解析、消除每条expense分类存储。
Main现有实现已经正确，拒绝替换仍可交付；采用应出于此具体结构改进，而非为了D标签。
本线仅提出并实证，Main需独立决定采用/拒绝以及最终交付验证。
