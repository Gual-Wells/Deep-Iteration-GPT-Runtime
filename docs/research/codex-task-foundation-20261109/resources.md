# V 领域：研究投入、可撤销承诺与成品粒度

本文件研究一个独立问题：在还不知道最佳路线时，怎样把投入用在能改变用户决定、最终交付及其品质的地方，而不让准备工作自然长成另一个庞大项目。它属于本次前置 U0 的研究材料，不是后续任务的执行契约，也不授权制作学习书或调用收费 API。

受控输入：本轮 `REQUEST.txt` 原话、用户已确认 L1 改 L3、前置研究后由用户明确确认任务说明和关键取舍再全面执行、已确认任务续做只问变化。执行依据为父线提供并冻结的 `0.6.0@4b092cf1e9817b1a80e408965a87d17c035950fd`。本文的办法是研究提案；不能冒充已经修改的协议或已经观察到的跨任务收益。

## 1. 领域怎样形成

我从“该不该再研究”进入，发现更值得问的是“下一笔研究要保护哪项尚可纠正的承诺”。同样两小时，花在确认用户要原页组装还是重写，可以取消数天错误工程；花在已选路线的元数据格式争论，却可能把用户锁得更深。投入是否合理，取决于它发生在何种决定之前、能使什么结果改变，以及替代的做法是什么。

这不等于每次研究必须即时进入成品。陌生领域可能需要一组材料和一次试作才产生有力解释。需要保护这种有界的探索，同时使继续投入有下一次面对材料和结果的机会。

我的当前主张：U0 应使人看见“最终拿到什么、现有什么可以直接用、哪些误解最贵、先花哪一笔来区分路线、什么时候转入制作”。不宜要求用户先替模型完成详细任务树、效益评分或成本预测。

## 2. 一手材料与证据边界

### A. 澄清的价值要连到行动后果

[Value of Information: A Framework for Human–Agent Communication，v1](https://arxiv.org/html/2601.06407v1)，实际阅读第 3–7 节、表 1 和 Limitations。论文用问题对最后行动的预期改善减去沟通成本来决定澄清。它的实验使用预定义动作与问题，沟通成本按轮数线性计算；因此不能证明开放工程任务能由模型自报概率自动算出“最优问题”。表 1 的 0.10、0.20 成本条件中，其收益低于最优基线，与文中一些全称式优势表述有距离。它支持比较提问后果的原则，不支持把未经校准的数字当批准门槛。

### B. 元研究本身也会挤占产出

[Learning to select computations，Callaway 等，2018](https://arxiv.org/html/1711.06892)，实际阅读第 2.1–2.2、4.3、5 节。论文说明精确元推理昂贵，并在模拟场景中把选择计算的时间计入总时间。它还指出，假设“下一次计算就是最后一次”的贪心方法会过早停止，因为一些决定要多次计算才改变。这里借用两项约束：U0 的研究也有机会成本；观察单元可以是一组能形成判断的工作，不能机械缩成每一次检索。

[Selecting Computations: Theory and Applications，Hay 等，2012](https://aima.cs.berkeley.edu/~russell/papers/uai12-meta.pdf)，实际阅读第 1–3 节。研究把收集证据与选择最终行动分开，指出逐步获得即时回报的 bandit 问题不能直接替代最终一次选择的问题；第 3 节给出候选排序依赖其它选项的反例。这提醒我们：不能给每条支线一个脱离替代路线的固定价值分数，也不能按“花过多少、获得多少材料”奖励继续。

### C. 并行会改变成本结构

[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)，实际阅读 Benefits、Prompt engineering、Evaluations 和 Production reliability。作者报告多代理适合可独立展开的宽度研究，也报告聊天、单代理、多代理的 token 消耗有显著差别，以及共享上下文和依赖密集任务的困难。文中的内部效果与用量倍数不应换算成本机 DIGR 的预期收益或账单。可迁移的是：拆分前应指出真正独立的问题、返回形态和汇合用途；并行缩短等待时间，不代表总资源更少。

[Towards a Science of Scaling Agent Systems，v1](https://arxiv.org/html/2512.08296v1)，实际阅读摘要、第 4 节架构/成本分析及第 5 节限制。它在四个基准和受控架构中观察到任务结构、工具与协调开销影响多代理结果；结果并非随人数单调改善。其架构、模型、预算和任务与当前宿主不同，部分公式还涉及标准化变量，不宜把论文阈值移作本项目人数或投入开关。这里只把它作为“人数不是资源价值代理变量”的外部反证。

### D. 先明确值得投入多少，再选择做法

[Shape Up：Set Boundaries，Ryan Singer](https://basecamp.com/shapeup/1.2-chapter-03)，实际阅读 appetite、fixed time / variable scope、calendar 案例。作者区分愿意投入的时间与对既定方案的估时，并从用户具体受阻情境收窄问题。其周期和团队规模是 Basecamp 实践，不能照搬为统一 U0 时限。可取的是：同一个用途可以有不同投入与实现路线；愿意花多少、预计要花多少、最低质量不能混成一项。

## 3. 资源决策先看三个对象

### 3.1 用户能够使用的最终对象

“整理资料”不足以确定工作单位。交付可能是可打开的组装文件、带岗位证据的行动清单、可运行的修复、研究论证、供决策的比较，也可能是用户明确委托的一套中间数据。应先取回用途和既有决定，再把预期结果说到可以比较小样的程度。

把中间数据一概贬低同样会错。如果用户要的是可复用语料库，语料结构就是成品；如果用户要读物，语料库就需要证明它为何是这份读物的必要路径。价值来自当前委托的用途，不来自产物类型。

### 3.2 下一项会使返工变贵的承诺

包括批量重写原件、选定承载格式、全量转换材料、扩成多条完整主进度、让大量工作依赖某个未验证接口。物理可撤销并不表示经济上容易纠正：十万字重写可以删掉，但已消耗的算力和延迟无法收回。

在该承诺之前，优先研究能改变它的问题。例如先比较“保留原页能否读顺”和“缺定义是否能局部补齐”，通常比先设计完整出版数据模型更能保护后续投入。反过来，已知任务确实需要跨格式检索时，数据模型可能就是决定成败的对象，应认真研究。

### 3.3 眼前最有用的反馈单元

粒度应围绕能暴露真实错误、能让人判断路线的整体确定。一个包括定义、正文、公式和跳转的代表片段，能揭示读物路线；分别做三十个术语条目可能暴露不了依赖割裂。粒度太大，会在用户纠偏前完成大量错误工作；太小，会得到许多局部精良而无法使用的零件。

这不是普遍的“越粗越好”。若一个错误数值会支配整个决策，就应追到该数值的来源与含义；若整篇创作的声音尚未出现，逐句打磨可能过早。判断问题是：这一单元独立完成后，用户或制作路线能得到哪种真实反馈？

## 4. 先核实已有基础，避免重复购买已有答案

只查会改变当前选择的资产，不先做全盘盘点。每项必要资产保留原位置、当前用途、实际核实范围和失败时的替代即可。

| 已有基础的情形 | 最小有用核查 | 对投入的影响 |
| --- | --- | --- |
| 已有明确选择和已验小样 | 打开对应成品/样本；确认适用于本轮用途且未被新纠正推翻 | 续做只问变化，不重开同一选择 |
| 文件存在，实际可用未知 | 取一个能暴露主要难处的真实片段试用 | 不按存在的文件数推算可省工作量 |
| 必须保留的原件或历史版本 | 核对身份、内容与版本来源 | 先找对原件；无法取得时保留缺口，不能用重写掩盖 |
| 有代码/工具，但新任务依赖它的新能力 | 对该能力做一次代表性调用或打开对应实现 | 不把“安装过”当“能完成当前工作” |
| 缺一项强依赖，且没有可接受替代 | 明确哪个结果被阻断，以及取得它需要谁做什么 | 可研究旁支；不让后续大批生产建立在假定存在上 |
| 基础可以替换、恢复成本低 | 说明当前默认与以后切换的后果 | 无需为可便宜纠正的选择开展全面选型 |

本仓库已有 `codex/WORKBENCH.md` 的普通工作笔记、受控输入和恢复包能力；`codex/examples/assembly/WORK.md` 也已经明确了原页组装与全文重排的竞争。它们是可复用的机制和构造情境，不是本次已制作读物或新 U0 已有效的证据。`schemas/u0-receipt.schema.json` 属于旧 stable 的文本/散列收据；单靠它无法表达用途、粒度、依赖与关键决定，且不能将 stable 生命周期偷接成本实验执行入口。

因此，前置建设宜先复用原话保存和普通笔记，再补缺少的用户决策内容。除非出现实际恢复或调用困难，不宜先建立第二套目标数据库、资产评分器或全自动预算平台。

## 5. 参数投入不能直接冒充成本估计

本轮 pinned 参数把 N/R/D/V 定义为责任，不能将其等同工具次数、字数、代理名额或货币。资源研究应把这组责任连接到实际问题与结果，不能反过来把任务切碎来消耗参数。

| 看得到的投入项 | 在 U0 中应说清的后果 | 常见误读 |
| --- | --- | --- |
| N | 哪类实质问题需研究、比较或制作到改变结果；粒度如何贴近成品 | N5 就列五个文件或五个步骤 |
| R | 哪些不同的中心问题值得重新研究整个候选 | 把三章校对算 R3，或三次重复同一检查 |
| D | 独立者将有机会挑战什么支配前提；Main 怎样处理替代 | 多派制作工单即可充数 |
| V | 哪些陌生领域值得持续研究；为何可能改变当前理解 | 分三个来源搜索员，末尾各提一句建议 |
| M | 每多一条均有独立主进度、完整研究和收敛责任 | 认为 M2 只是两个人分摊原总量 |
| T/t | 实际 MAIN/SOURCE 区间、软硬策略、计时能力 | 将墙钟、团队总投入、账单互换 |

尤其注意：独占 D/V 不进入 Main 的 T/t，并不等于它们没有资源消耗。并行 3 名代理各工作 10 分钟，不能声称只投入了 10 分钟总人力/算力，也不能在没有 token 或计费数据时编成 30 分钟可比模型成本。本协议的计时事实、资源足迹和实际费用应各按能够观察的口径报告，未知保留未知。

愿意投入的上限、预计所需投入、协议承诺的下限应分开。软 T20min 不能被当作“总成本最多20分钟”，达到软时间也不能代替完成。若真实预算与已承诺责任不相容，需明确呈现冲突和可选范围；不能静默降低单位重量、下调参数或伪造完成。

本次元工作有自己的目标与投入；后续主任务另行在其已确认范围内形成投入安排。不能把本次文献阅读假称已经完成了后续任务的调研，也不能让后续任务自动继承本次高投入参数。

后续用户已进一步明确：前置独立预算与计时，正式调用参数留给正式任务；前置按规模、歧义、已有基础和返工代价动态研究，并说明结束条件，显著增投再讨论。上表解释的是正式责任的资源后果，不能变成前置阶段必须再填写、承诺或消耗的一组 N/R/D/V。前置先说研究对象、资源范围及返回点，正式参数待确认后的正式阶段解析与初始化。

## 6. 一种可实施的投入讨论方式

不用评分表，只在会改变选择时补全以下一段意思：

> 你要拿到的是〔可使用对象及范围〕，最重要的是〔一两项质量〕。已经有〔实际核实过的基础〕。目前最贵的误解是〔路线分歧〕；先用〔一组材料/代表性试作〕区分它。若出现 A，就〔具体继续方式〕；若出现 B，就〔替代/停止方式〕。这笔前置工作占用〔可观察的时间、并行规模、外部费用及未知〕；做到〔可见结果或明确限制〕后，先向你呈现取舍，再进入〔全面执行范围〕。

它是工作解释的内容，不要求所有任务填同一表单。已确认继续任务可以缩成变化：新目标、新原件、新限制、上轮结论是否仍适用。对能直接从材料查明的事情，模型先查；对用户价值取舍，展示具体差异后问用户。不得把此段变成每轮重新授权。

估计暂时很粗时，给条件范围及最大不确定来源。例如“原页直接组装的工作集中在选段与跳转；若公式缺定义且跨章补入仍不可读，局部重排的范围会增加”。这比没有测量依据的“成本2.3、收益8.7、置信度0.91”更能支持纠偏。

## 7. 怎样停止研究，又不把研究做浅

应当结束的是一笔具体研究或一条已失去用途的支路，不是宣称所有未知都清零。

1. **已经能改变或稳固关键选择。** 展示比较物、证据、保留缺口及代价，进入用户决策或已授权制作；不继续收集同质来源，只为增加确定感。
2. **下一笔结果无论怎样都不改变做法。** 先停止该支路。若理由是难以想象反例，改问“什么材料可能推翻这条路线”，而不是直接断言研究无价值。
3. **需要一组工作才能得到反馈。** 给这组探索一个具体对象和返回点；允许阅读、比较、试作相互推动。不能要求每个打开页面都立即证明收益。
4. **预算或真实能力已到边界。** 返回已经知道什么、尚不知道什么、继续需要怎样的范围或资源。预算耗尽不等于原问题已经解决。
5. **阻断事实尚未取得。** 让该依赖保持未满足，继续不依赖它的部分；不要把继续铺设支撑文件当成接近成品。

禁止递归：不能为“如何停止 U0”再造必须先完成的第二层 U0、评分器训练、全量经验库或持续监控。只有当这些是本轮委托范围内、且有实际困难需要它们时才建设。本次研究的独立成品是能让用户做第一系列关键决定的任务说明、比较材料和可执行安排；不以偷偷推进后续任务来证明元工作有用。

## 8. 具体对比样例

以下为构造对比，不宣称真实用户在本轮委托这些任务。

| 情境 | 容易耗尽投入的路线 | 更能支持决定的一笔工作 | 应给用户看的差异 |
| --- | --- | --- | --- |
| 从数份原件组装可读文件，保留内容 | 先全量OCR、统一结构、拆术语、重写每一节 | 取包含图、公式、定义依赖的片段，用原页路线和局部处理路线各作能比较的样本；本轮仅设计对比，不制作学习书 | 同一学习过程哪里顺、哪里断，哪种做法增加何种处理与损失 |
| 用户指定导出一个历史版本 | 先分析并修复当前版本，再讨论回滚策略 | 核实指定版本身份、取得原内容、检验导出是否一致 | 指定原版本与当前版本区别；是否缺资源。无需把本次扩大为当前版本重构 |
| 已知输入交错导致搜索列表倒退 | 先建通用日志平台、缓存框架、全站基准 | 用相同输入时序对齐请求、响应与渲染，区分旧响应覆盖与缓存解释 | 两条解释各自能解释什么；修复后同一行为是否改变 |
| 多城市岗位调研，信息可独立核实 | 一人顺序重复所有检索，或十人按同一关键词扫同一公司 | 按真正独立的地区/机会问题并行，统一“当前在线/近期动作/未知HC”等证据性质，主线形成行动入口 | 事实覆盖扩大了多少、哪些机会仍不可证、汇合是否及时形成可行动清单 |
| 开放创作尚无整体声音 | 先逐句修辞评分、逐词优化 | 围绕不同说话者/构形做有实质差异的短试作，再选择值得发展的整体 | 用户读到的力量与偏好如何不同；无需把陌生探索压成即时投资回报 |
| 已有成品与确认要求，用户补一项局部变化 | 重新访谈全部目标、重做文献与资产盘点 | 核对变化影响的局部依赖和既有结论 | 变化会改变的范围、代价和使用效果，其余已决定内容直接沿用 |

### 一项有数字的构造演算

假设下一步全量处理 40 份文档，眼下有 A“保留原页”、B“全部重排”两条路线。无法可靠估计用户偏好概率，也不知道每份材料的完整处理成本。可以先花 15 分钟取得同一代表片段的可比较结果，并向用户呈现差异；这里 15 分钟是演算假设，不是本项目统一门槛。若小样揭示必须重排的是少数公式页，便把全面处理对象收窄到实际问题；若反而揭示原页无法使用，则有据选择 B。

错误演算是“40份×每份1N，先执行40N再问”。它把数量误当粒度，把用户本来可以早纠正的承诺推迟到大部分资源已经花完之后。另一个错误是“15分钟还没证明收益，立即停止所有探索”：若必须组合三种片段才暴露阅读依赖，一组完整试作才是合适的观察单元。

## 9. 失败反例，用来检验主线候选

| 候选若出现这种写法 | 为什么失败 | 需要实际改变什么 |
| --- | --- | --- |
| “已确认目标：建设完整知识库”，原话只要一份组装文件 | 把手段升格成未经确认的新成品 | 拿回用户用途；用具体样本显示知识库是否必要，再由用户决定 |
| “所有字段填满后才能启动” | 可便宜纠正的信息也变成阻断；无材料的用户被迫编造 | 允许未知；只追影响路线和昂贵返工的问题，先查已有材料 |
| “VoI>0.6 自动执行，否则继续问” | 无校准概率、效用单位与沟通成本，门槛是伪精确 | 展示不同回答会改变的行动；有实际测量才使用数字 |
| “已阅30篇，因此前置研究充分” | 材料数量与关键决定的质量无直接对应 | 指出哪条选择被支持/推翻以及剩余缺口 |
| “D/V不计入T，所以可以无限加人” | 协议计时口径被误读为成本免费 | 告知并行规模、真实足迹与未知，只有独立问题值得展开才增投 |
| “用户没回复，按推荐项全面生产” | 本任务要求明确确认，沉默不能替代 | 保留待确认选择，只做不依赖它的授权研究 |
| “节省投入，所以所有任务都只做最小样本” | 深度研究、复杂依赖或高品质成品可能确实需要大量工作 | 对决定品质的困难投入；用反馈修正范围，不预设最低工作量 |
| “已有文件，因此复用率90%” | 没证明版本、用途、内容和能力仍适用 | 对决定路线的代表资产作实际核实，不能由文件数生成可用率 |
| “先把这个元框架研究完美，之后一定能省” | 无实际返回点且训练/管理成本不断自增 | 交付本次可用的用户决策材料；候选在真实场景中暴露困难后再补能力 |

## 10. 当前可带回主线的取舍

建议采用：以可用结果定义粒度；检查能改变当前选择的已有资产；把前置研究和后续生产的投入分开；把参数责任、团队足迹、费用口径分开；每笔投入说明它面对的决定和返回点；以具体比较支持用户关键决定。

建议拒绝：统一效益分数、固定澄清轮数、固定资源百分比、按原件数量换算 N、把多代理论文倍数当本机成本模型、在没有主线候选之前先建完整预算执行器。

还应等待主线候选后再入：检查它是否真的让用户在大额投入前看懂取舍，是否只多了一份模板，是否保护了有内容的探索，以及已确认续做是否仍被迫重做全部访谈。本文首轮形成了领域、原始材料与可实施判断，尚未冒称已经验证该候选的实际交互效果。

## 11. V 同线再入：C1 形式完整，仍可能目标不全

父线已转交完整 C1：`原话 + 可修订任务说明 + 问答决定`，任务说明具备 goal/results/scope/granularity/basis/dependencies/approach/resources；使用现有会话目录中的 `foundation.json` 和 propose/show/answer/confirm；正式初始化等明确确认，续做只处理变化。

C1 已解决可取回、修订与确认对象一致的问题，我保留这些成果。它尚未解决的中心风险是：八个字段都可能认真填写、用户也可能确认，但它们共同指向的仍是一条把绝大部分工作压在中间原料上的路线。确认版本正确，不能证明该版本在承载用户真正想要的成品。

例如以下构造稿可以形式完整：

```text
goal：把前置U0工程化，让后续任务目标完整。
results：八要素任务说明、问答记录、确认状态和CLI。
scope：本仓库Codex实验通道。
granularity：按八个字段分别建设提取、编辑、保存和检查能力。
basis：已有REQUEST冻结和会话工具。
dependencies：已有Python环境；用户答复。
approach：先完成结构与全部CLI，再编写交互说明，最后演练。
resources：前置独立计时；正式参数确认后初始化。
```

即使每项非空且被明确确认，它的最早可见成果仍可能只是字段和命令都齐全；没有展示“现成资料怎样改变理解”“过细中间工作怎样被取消”“用户纠正怎样改变下一步实际生产”。这不是多加一个校验条件能修好的问题：它的生产顺序和完成单位就需要改变。

### 补入的一手研究与反例

[Shape Up：Get One Piece Done](https://basecamp.com/shapeup/3.2-chapter-11)主张尽早把一个核心部分集成到可体验的程度，而非把多层零件留到末尾汇合。值得保留其证据限度：书中可见性开关早期能保存状态，却尚未改变真正访问权限。这一小样能判断交互，不能证明访问控制正确。因此，本项目不能把“问答看得见”当“全面执行边界已有效”。

[Map the Scopes](https://basecamp.com/shapeup/3.3-chapter-12)把独立完成范围系于实际依赖，而非人员分工；同时承认有些复杂后台需要独立研究。可迁入的不是一律切小，而是让工作边界由真实关系长出来。它为下面的整体替代提供构形，未证明对本项目的效果。

## 12. D 成熟介入：用交付路线和整体候选组织投入

**争夺的对象：C1 的主组织方式与生产顺序。** 主张把“填齐八要素、保存并确认”改为“研究形成可比较的交付路线，让用户对看得懂后果的当前路线作决定；工具保存与恢复这个决定”。八要素继续作为覆盖内容，小文件/CLI继续作为载体；它们不再定义完成单元。

替代的整体路线如下：

```text
原话与既有决定
    ↓ 先取回会改变理解的真实基础
两种有实质差别的交付路线（确有分歧时）
    ↓ 用代表材料/小样解释粒度、依赖、工作量及放弃什么
用户看得懂的当前任务说明 + 少量关键问题
    ↓ 用户纠正真正改变说明和下一项动作
明确确认当前交付范围与取舍
    ↓ 正式解析/初始化、生产、验证
恢复时取回当前决定，只处理实质变化
```

这是一条工作路线，不是新固定状态机，不要求每个明确任务都制造两个方案。已有足够依据的直接任务应呈现简明说明；创作、探索或中间数据本就是用户成品时，以该用途确定整体候选，不强制做一个可发布产品。

### 12.1 第一份应先做出的整体成果

本轮应先做成一个真实可走通的“新任务 → 研究后解释 → 用户纠正 → 修订 → 明确确认 → 正式入口”的完整交互片段，并再走一次“已有确认 → 只改变化 → 续做”。它必须包含一种会把任务误导向中间原料的具体错误解释；纠正后产物形态、处理粒度或路线实际改变。先让这个片段暴露需要保存和恢复的内容，再实现它实际需要的最小载体与命令。

不按“goal字段已做完、results字段已做完、answer命令已做完”报告实质完成。技术层的开发任务当然可以这样拆；面对用户的进度和验收应能指向一个已经能理解、纠正并继续执行的整体过程。

### 12.2 可直接供主线改写的本任务说明小样

下文是一份构造的用户审阅稿，不是用户已给出的确认，也不代表主线已实施。

> 这次建设完成后，新请求会先形成一份基于原话、现有资料与独立研究的任务说明。你能在全面开工前看清最终拿到什么、哪些内容做到什么粒度、先复用哪些基础、主要依赖和资源去向；纠正其中一项后，下一步操作会随之改变。确认后才进入正式调用的参数初始化与生产。已确认任务继续时，只讨论重要变化。
>
> 我们已有请求冻结、普通工作笔记和会话恢复能力，可以复用。当前缺少的是研究后的任务说明及其问答决定能否稳定带入正式入口；已有恢复工具不证明这个过程已经有效。
>
> 可以走两条路线：A 先做完整字段与命令，再补交互；B 先把一次关键纠正与一次续做走通，再补其需要的保存和入口衔接。A 较早有齐全结构，却可能把内容偏差留到最后；B 较早暴露用户是否看懂、纠正是否影响下一步，但要在演练后再确定部分字段。建议B，保留能取回和修订当前决定的小型载体。
>
> 前置研究独立预算与计时。研究深度取决于任务规模、歧义、已有基础和误判的返工代价；本轮返回点是你能比较路线、指出需改之处并确认当前任务说明。若关键依赖未取到，就呈现限制，不把它伪装成完整；若发现需要显著增加研究或建设投入，先说明新增问题和资源后果，再讨论。正式N/R/D/V不在这一步消耗。

这份说明的关键问题可以是：

> **本轮你要的完成结果更接近哪一种？**
> A. 先交付一套可供后续实现的研究和流程设计；当前不把正式入口接通。
> B. 完成实际工程接入，使新任务、纠正和续做能沿这条流程运行，并给出走通证据。
>
> 选A会使当前结果停在研究/设计；选B会增加必要实现与真实调用验证。原话中的“设计与建设”更支持B，这仍须结合本轮已有答复作当前解释，不能把这里的示例答复冒充真实确认。

用户已经回答过的相同取舍必须直接沿用；这个问题只用于说明怎样把“建设”具体化，不能因此要求父线重问现有决定。

### 12.3 让“粒度过细”真正改变下一步的演练

仍用构造情境，不能写成用户本轮发生过的对话：

```text
原始请求：把已有项目材料整理成一份可以直接交给维护者的接手说明。

错误初稿：逐份材料提取全部术语和知识原子，建立统一分类，
          等所有材料结构化后再生成接手说明。

实质问题：维护者第一次接手时，你更需要完整术语库，
          还是能找到启动入口、当前行为、关键决定、已知问题和恢复办法？
          前者把大部分工作放在全量原子化；后者按真实接手流程组织材料。

构造答复：先能接手；已有说明和代码直接引用，不重写全部材料。

修订后的实际路线：先用现有启动说明、一个关键决策和一个已知问题，
                  形成一段可沿链接操作的接手流程；核实依赖与缺口；
                  再补齐其他关键范围。取消全量术语拆解和统一分类任务。

正式执行的完成对象：维护者能按接手说明定位并完成约定操作，
                    关键未知与限制明确。不是术语条目达到数量。
```

这里发生的改变是取消了一条大规模中间生产路线，转向用户需要的整体对象；不是多留一句“注意不要过细”。已有基础直接进入成品，所以研究还会检查这些引用是否真实可用。若用户真实要的就是术语库，便应保留原子化路线，不能把本例升格成永久禁令。

### 12.4 资源如何随这条路线动态变化

| 实际发现 | 投入怎样变 | 下一次面对什么结果 |
| --- | --- | --- |
| 目标和基础清楚，已有小样仍适用 | 直接沿用；缩短前置，不重做独立文献研究 | 只呈现本轮变化及其后果 |
| 不同解释会导致完全不同成品 | 优先研究和展示这项分歧，暂缓其下游批量生产 | 同一用途的可比较路线或代表样本 |
| 成品已明确，但缺一项关键依赖 | 把投入放到该依赖的真实取得或可接受替代 | 该依赖支持的行为及仍未满足之处 |
| 研究要多项材料连用才能区分路线 | 给一组完整研究机会，保留其返回点 | 有内容的解释/试作，避免逐检索论功 |
| 方法开始要求新平台、大规模转换或显著扩线 | 停在新增承诺前说明原因与资源后果，讨论是否扩大 | 新旧路线能提供的结果及代价差别 |
| 既有路线成立，下一材料不会改变选择 | 结束这条研究，进入已确认的生产范围 | 实际成品，不再用来源数量充实准备 |

前置到达返回点后还要满足用户已要求的明确确认。模型认为研究够了，只能决定“现在有条件向用户呈现决定”；不能据此替用户批准全面开工。若用户要求继续研究某一关键问题，就按其范围继续。

## 13. C2 同线再入：核心替代已落入，仍须看真实说明

已实际读取当前 `codex/FOUNDATION.md`、`runtime/codex_foundation.py`、`runtime/codex_session.py` 的相关接入口及 `tests/test_codex_foundation.py`。本次只作内容/代码阅读和下列说明小样，不宣称已运行主线CLI或观察真实用户效果。

核心替代已经落入 C2：工作先组织完整可辨的结果及最早整体候选；字段、命令、中间件不充当完成单位；资产须有实际取得/打开/运行的范围；前置按问题动态投入，与正式责任和时间分开；准备文件不等于开工。`foundation_packet` 会把当前说明带入恢复入口，代码也明确不判断自然语言意图质量。因此无需再扩一套资源框架。

仍需认真面对的两个高影响问题如下，不把它们合并成“再加检查”建议：

1. **纠正必须进入当前说明，不能仅写在 effect。** `answer_foundation` 保存原话和 effect，却不会改写 brief；全部问题已答后，同一修订仍可以被确认。若用户纠正“我要接手说明，不要术语库”，只在 effect 写“已取消术语库”，旧 results/approach/completion 仍可能进入正式执行。辅助工具不应猜自然语言，但主线演练必须真的 `propose` 改写后的整份说明，再显示和确认；不能将 effect 的自述当已落实。当前测试有第二次 propose，方向正确；第14节小样用于把占位字段换成可读的完整对象。
2. **待决增量与原范围续做存在保守程度差别。** FOUNDATION 文字允许不依赖变化的原确认工作继续；目前一个 material 提案会清空全局确认，使所有正式 begin/checkpoint 均被挡住。若要保留原范围续做，应先把未决建议作为尚未生效的讨论，不把它直接覆盖成当前正式说明；否则需明确说明辅助入口暂按整份任务保守暂停。不能一边称“原范围可继续”，一边让实际入口只能全部停止，也不能用 non_material 将实质增量混进旧确认。此处没有要求新建分层状态平台。

第一项也是“已确认中间件冒充成品”尚会发生的位置：它不能靠JSON完整或CONFIRMED根治，而须让当前可读说明及后续实际动作一直指向用户的结果。若用户明确选择中间材料本身为阶段成品，说明应写清该阶段的用途与如何接到整件事，不擅自拒绝其选择。

## 14. 可用于实际 CLI 演练的完整说明小样

这是隔离演练材料，不是本轮新增用户委托、真实用户答复或真实开工确认。构造原始请求为：“把这个仓库交给新维护者，做一份可以直接使用的接手说明；已有内容直接引用，别重写所有资料。”演练不得据此替真实用户确认或启动另一个任务。

完整理解是：维护者需要沿一份说明找到入口、看懂当前决定并完成约定接手操作。先拿既有入口组成一条可走的接手链，再补齐其余关键范围。逐份拆解全部术语、建立统一知识库没有进入这条交付路线。若用户只需概览，应实际改写结果、粒度、路线和完成行为，而不是只把该答复附在下面。

下面代码块可提取为 `foundation propose --input` 所需 JSON；所有成本和未运行项均以本例假设/已核实范围说明。

```json
{
  "brief": {
```
