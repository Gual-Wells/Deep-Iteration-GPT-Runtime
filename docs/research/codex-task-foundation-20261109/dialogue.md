# U0 对话研究：让用户在大投入前看清并改变任务

研究身份：独立 V 侦察；持续领域为**共同理解、对话修复与设计意图的共同形成**。输入仅为本轮原始请求、已确认约束与 `0.6.0@4b092cf1e9817b1a80e408965a87d17c035950fd` 协议包；未读主线推导。首轮是候选建议，尚未收到主线工程候选，也未验证实际宿主对话。

## 研究主张

U0 的关键产物是用户能据以纠偏、选择并明确确认的任务说明。模型先承担整理已有材料、提出有根据解释和制作代表性小样的工作；问答围绕会改变成品或投入的具体选择展开。说明可以完整，但不能把内部字段清单转成用户必须逐项填写的表格。

“理解了”与“同意执行”需分开：普通沟通中的理解证据不能代替本用户明确要求的执行确认。反过来，确认也不证明用户已理解一篇冗长说明；要把影响使用的差异与代价摆在确认对象旁边。

## 可执行的问答策略

### 1. 先形成一份模型负责的草稿

先从原话、已有文件与已确认决定填出用途、完整交付、范围、粒度、材料依赖和大投入发生点。缺少信息不立即变成提问：先判断能否查证、暂定、用小样辨认，或必须由用户决策。保留原话入口，不用改写后的描述覆盖原件。

展示时不必暴露所有内部字段。用户先看到：完成时会拿到什么、能用来做什么、一个代表性实例，以及当前最影响结果的一处分歧。说明中的模型推断明确标为暂定。

### 2. 一轮围绕一个决定，可以并列少量真正独立的问题

问题包括三个要素：**具体对象、可理解的差异、选择的后果**。例如不要问“工作细粒度是什么”，而展示“以整条可用流程完成”与“先深入一个独立模块”的可见差别，说明后者会推迟完整结果。开放答复始终有效；选项是帮助辨认，而非封闭答案空间。

下一问题取决于回答。用户说“都不是”时，先修复问题表征；不顺着原清单问下去。用户说“你决定”时，模型按已有用途给出理由并标清暂定决定，但本用户要求的最终明确确认仍待取得。

### 3. 小样为决定服务

若关键差异只能通过体验说明，制作最小的完整代表片段，并同时说明它会怎样扩展成完整结果。例如 U0 的小样是“一条实际请求如何变成可纠偏说明、如何处理答复并进入执行”，而非先造模板平台、记录平台和复杂字段系统。

小样投入前须能说清：它将帮助哪项选择；什么反馈会改变方向；到哪里停。若没有任何可能反馈会改变方案，这个小样只是展示，不能当作必要澄清成本。

### 4. 回答必须产生可见后果

短答也可处理：

> 用户：“别让我决定模块，给我最终能用的结果。”
>
> 系统：“任务粒度改为一条可用流程。原拟独立交付的说明生成模块并入流程验证；确认前只展示流程小样。下面的任务说明已据此改为 v2。”

这比“收到，已记住偏好”更有用。若已产生成果受纠正影响，需实际修订或撤下；仅改今后的规则不算处理完成。

### 5. 用有边界的确认结束 U0

确认对象是当前版本的完整任务说明及关键取舍，不能只是一个空泛的“是否继续”。用户可以确认、改一点后确认、要求更换方案、保持讨论或停止。

明确确认后执行不再重复同范围问题。出现目标、成品边界、重要成本或关键依赖变化，才针对变化重新讨论。沉默、等待超时、内部自评通过、用户只回答局部问题都不替代该用户要求的完整确认。

## 当前任务的具体小样：供主线落地的候选

下面是说明内容与对话的小样，不是已经确认的工程范围。尤其“可运行到何种宿主能力”仍应由主线核对后形成选择，不能在本研究里偷定。

### 任务说明 v0.1

**原始目的（用户原话摘录）**

> “让整个任务在全面开始前就能让我完成第一系列关键决策的理解与纠偏，用以防止大量算力投入到非完成品目标的中间阶段的过度细粒度工作中”

> “本次任务专门进行该部分的研究探索下的设计与建设。”

**已确认的共同事实（由主线提供，本线未另行推导）**

- 本轮专做 DIGR 前置阶段，不制作学习书。
- 参数末位隔离要求为 L3。
- 前置研究后的任务说明与关键取舍须由用户明确确认再全面执行；已确认续做只问变化。

**当前解释（模型提出，可纠正）**

需要建设一种可重复使用的前置工作方式：面对复杂请求，结合已有材料和独立调查形成完整任务说明，让用户理解成品、范围、粒度、依赖和投入路线；通过针对关键分歧的问答修正，并在明确确认之后进入全面执行。前置工作本身有边界，也要把主要投入留给最终可用结果。

**完成时用户拿到什么（候选，待主线结合实际能力核实）**

1. 当前实验 profile 中可供下一次任务实际采用的 U0 说明与行为；入口和对后续执行的交接明确。
2. 一条真实演练：原请求 → 有依据的任务说明 → 关键问题 → 用户纠正后的说明 → 明确确认或保持等待；可看清什么实际改变。
3. 用户只需面对当前任务说明和必要决定；研究依据及验证记录作为可查附件。

**工作范围与粒度（候选）**

以“用户可用的整条前置—确认—交接流程”为完成单位。先在现有能力上补足必要行为，再决定是否需要新增专用工具。只把会显著影响成品、返工或成本的子问题拆开；不默认拆成每段文字、每条资料、每个字段的独立生产项目。若某项未知确需较大探索，说明它为何关系成品、预计投入边界和何时向用户返回选择。

**已有基础与依赖**

当前 pinned profile、原始请求和已确认纠正为共同输入。现有代码、工具和测试可复用到什么程度，需主线实际查证；本线没有据此声明已兼容。来源调查帮助判断选项，不替用户决定用途。此阶段不依赖未来学习书或其他下游作品已经制作。

**关键质量**

用户能在大投入前看清完整结果与重要取舍；纠正改变下一行动和已有说明；原话、模型解释和决定可区分；明确确认不会被误判；确认后的常规续做不反复重问；元工作不会无限扩张。

**投入说明（模型研究建议，非新预算授权）**

说明各路线会把工作花在哪里、已有基础可省去什么、什么未知可能迫使重开，以及较便宜的试作能否减少误投。动态 DIGR 参数仍按本轮 pin 的真实语义承担，不能把参数调低来绕过职责，也不能把高参数自动翻译成新增付费授权。成本未知时诚实写未知；不伪造 token、时长或准确概率。

**进入全面执行前尚需作的决定**

确认实际建设边界与资源路线。此示例不以“内容完整”为由自动开始实施。

### 与上述说明配套的一轮问题示例

> 按这份说明，下一次复杂 DIGR 请求会先得到可纠偏的成品说明和关键选择，再明确确认后开展全面制作。现在需要决定的是本轮建设到哪一层：
>
> A. 先把这条完整交互写进现有 profile，并用真实请求演练确认与交接；用户直接在聊天里使用。
>
> B. 除了聊天行为，还建设本地命令来保存、更新和读取任务说明；会增加工具实现及维护工作。
>
> 两者都应交付完整可用流程。你也可以直接指出这份说明哪里错了，或描述另一种使用方式。

这是可供主线适配的问题结构。是否推荐 A、B 的实际增量成本、现有工具是否已覆盖 B，需要代码证据；本线未把未经核实的路线包装为确定推荐。

### 续做变化的问法示例

> 已沿用你确认的任务说明 v2。新发现是现有工具无法保持确认后的版本，继续按原路线会多出版本维护成本。当前方案改为复用已有工作包保存版本，成品和确认规则不变；这会影响你此前选择的工具维护范围，需要只确认这项变化。

若新发现并不影响已确认目标或关键取舍，则不借“变化”重新索取整份授权。

## 有界建设与最小验证

U0 退出条件是：完整结果可辨、关键分支已研究到足以选择、会改变大投入的用户决定已取得、说明的待定项不再阻碍下一阶段。细部可以留到执行中，只要不会把成品目标换成中间项目。若用户尚不能决定，下一步应返回更有帮助的代表片段或竞争方案；若收益不足，就明确保持待定，不无限堆研究。

主线的最小验证应当使用有行为差异的例子：原话明确者不被重复盘问；有关键歧义者被展示具体差异；用户否定原解释后下一行动改变；只答局部问题或沉默不能触发全面执行；已确认续做保留原决定；范围或成本大变后只重问受影响决定。文件存在、字段齐全和测试全绿均不能替代这些可观察行为。

## 同线再入接口

收到主线最小必要候选后，本领域继续研究三件事：用户能否从当前说明辨认最终结果；问题是否真的改变路线而非迫使填表；实现是否把理解证据误判为执行确认。需要候选正文、实际问题以及确认/变化处理的代表性记录即可，不要整份主线研究史。

## 同线再入与 D 介入：把“确认表单”替换为对成品的共同决定

### 本次材料与事实边界

本次实际读取了主线 `WORK.md` 的完整 C1 与共同确认。新增共同事实为：前置预算与计时独立，正式参数留给正式任务；前置按规模、歧义、基础和返工代价动态研究，说明结束条件，显著增投再讨论。本线仍未读取其他代理私有推导，没有浏览真实宿主用户消息日志，没有运行 CLI。以下对话全部是**交互试作**；不能作为已发生的用户答复或确认。

延用本领域已读的共同理解、mixed-initiative、Qulac、设计问题—方案共演化和 HAI 原论文。本次实质工作是将这些认识用于 C1 与竞争交互的逐情境比较，没有声称新增论文证据或已经观察到真实用户收益。

### 明确主张及替换对象

**保留 C1 的小型持久化路线 B；替换其用户交互的组织中心。** C1 的八个内部字段和 `propose/show/answer/confirm` 适合保存状态，不应成为用户必须经历的八项盘问或四段手续。主张采用 C2：**先给完整、可辨认的成品说明；只提出会改变结果的选择；把确认绑定到用户实际看过的决定；随后带着这些决定继续。**

C1 本文没有明说必须逐字段询问，因此不能把填表错误当作已经发生。但它尚未明确限制“字段缺失就问”和“任何修订都重走确认”；这两种实现非常容易把本来正确的记录机制转成官僚流程。本介入要求把限制写成实际行为，并在演练中验证。

最值得保留的 C1 能力是原话不可被解释覆盖、完整说明可取回、真实答复可追溯、受管理入口不越过未确认的重要变化。最值得替换的是以记录完整性驱动问答的倾向。用户没有义务补齐模型方便保存的分类。

### C1 与 C2 的实质比较

| 当前情境 | 只依 C1 结构可能采取的动作，不代表已经发生 | C2 的具体动作与选择依据 |
| --- | --- | --- |
| 用户已说清用途、形式、资料，只有实施细节未知 | 为补齐 basis/dependencies/approach 再向用户逐项询问 | 先查已有材料，说明已知与未知；实施细节由模型负责。不存在能改变成品的用户分歧，就直接展示说明并请求最终确认，不造问题。 |
| 用户只说“做个复杂东西”，自己也不能描述全部要求 | 把缺项一次性列成问卷 | 先拿一个有内容的整体候选或代表片段，问“哪种结果更接近你实际要用的东西，哪里不对”；再据反馈改变说明。 |
| 用户回答一个局部选择：“第二种” | 若实现把 answer 当完成信号，可能误开工；若一律不算，可能再堆手续 | 这只解决对应分歧。系统更新完整说明，突出改变与后果，再请求一次明确执行确认。 |
| 用户已看过完整说明，说“把本地页面改成 Markdown，其他按刚才的做，开始” | 若严格要求确认命令，可能无价值地再问 | 这已是对已看过说明及明确差异的执行指令。记录实际原话、原说明与差异，不要求魔法口令。若其后才引入新的重要取舍，则新取舍另议。 |
| 已确认后修正文案，或查到材料真实位置 | 把版本号变化当旧确认全部失效 | 更新事实记录或解释文本；如未改变交付、关键取舍、投入边界和用户义务，沿用原决定继续。不要伪造用户曾看过新文字。 |
| 已确认后发现需要新增付费依赖，或方案改成先做工具而推迟成品 | 只保存成新版本，再询问整份说明是否批准 | 清楚展示该变化、原因、代价、替代与影响。只对这项重要变化取得明确确认；原已确认部分继续有效。不得先实施变化再补确认。 |

C2 的成本是模型必须真正判断什么会改变用途与投入，不能只用版本号机械决定。对应保障不是新建审批平台，而是留一句可核对的变化理由，并用明确会改路线的情境验证。C1 的结构适合保存这种判断，不能代替判断。

### 续做与修订确认的明确规则

1. **接续首先取回决定，不首先重启问卷。** 带回已确认的完整说明、对应真实答复及尚未解决的重要问题。普通续做和恢复不以新版本名义再问原选择。
2. **说明的文字版本与用户决定分开。** 更正字词、查实路径、补充不改变决定的依据，可以更新记录并说明来源；不能声称用户曾逐字确认新文字，也不能自动让其原决定作废。
3. **实质修订按变化范围确认。** 交付、用途、关键质量、先做中间系统而推迟成品、显著新增投入或用户负担的变化，展示影响并取得明确决定。记录要能把基础说明与新差异连起来，不能把旧确认直接冒充对未见新方案的确认。
4. **局部答复保持局部效力。** “A”“不是这样”“改短一点”只承担其实际表达的意思。用户已看过完整对象并明确说改后执行时可以成立；不靠语气猜同意，不强求特定命令。
5. **修订未定不冻结无关工作。** 未确认的重要变化不得擅自实施；仍可在原已确认范围内完成不依赖变化的工作。若变化让整个旧路线失效，则停下该路线，带回具体选择。

这些规则不要求脚本理解所有语义。模型负责区分变化并提供理由，工具保存所依据的说明、差异和真实用户指令；工具验证不能自动签发语义确认。

### 问题 1：已确认的默认展示仍出现重新确认话术

### 问题 2：重要修订的变化理由被保存，却未进入默认说明

`propose_foundation` 把 `change_to_next`、`change_kind` 放入 history。默认 `foundation_packet` 不读取 history，只展示当前完整字段和当前 confirmation。

本次第二个内存情境为：原来已确认本地轻量保存；新提案改成外部付费服务，history 中明确写有“本地保存改为外部付费服务，需要重新讨论成本”，并设为 material。真实 renderer 的输出有新方案及 `AWAITING_USER`、`null`，但没有该变化理由。检查“该变化理由是否在输出中”的结果为 False。

因此，默认 show 尚不能单独支持协议规定的“先展示影响，只对变化问答”：用户需自行记住旧版并在全部字段中寻找改动；恢复中的模型也容易把它当成整份任务从未确认。作者可以把差异手写进字段来弥补，但默认入口仍未把已保存的最小必要信息带出来。

**建议的最小收尾：** 在当前完整说明之前，展示最后一次作者说明的变化、原因及原已确认范围如何继续适用；若重要变化尚未决定，直说“本次需要决定的是这项变化”。直接复用现有 change reason 与确认来源即可，不要求自动理解差异。若其影响尚未写清，模型负责补充这句话，不让脚本假装判断完成。
